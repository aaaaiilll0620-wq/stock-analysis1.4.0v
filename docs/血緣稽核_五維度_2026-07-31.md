## 4. `real_composite` 是否含 dynamic weights / regime —— 確認結果

### 4-1 程式碼層(確定)

`beat_0050/realbody/build_realbody_scores.py:133` 存的 `real_composite` = `score_row()['composite']`
= `score.total_score`,而 `core/score_store.py:206-207`:

```python
advisor.current_regime = _regime_at(as_of)        # ← regime 進來了
advisor.advise(stock, fund_res, val_res, score)   # ← in-place 覆寫 total_score
```

`core/advisor.py:advise()` 的順序:

| 步 | 行 | 動作 |
|---|---|---|
| 1 | :90-91 | **washout 覆寫籌碼 bucket**:`chip_bucket = min(100, max(whale,60)+5)` |
| 2 | :95 | **估值資料不足覆寫**:`val_bucket = 50.0 if '資料不足' in status` |
| 3 | :106-109 | **regime 乘數**:`mw = mode_weights × regime_multipliers(current_regime)` |
| 4 | :114 | **per-stock 動態權重**:強勢多頭排列 → 估值權重砍 60%,60% 給動能、40% 給籌碼 |
| 5 | :119-120 | `composite = Σ buckets·mw / Σmw` → 寫回 `total_score` |

**答案:是。`real_composite` 同時包含 regime 乘數與 per-stock 動態權重,而且還包含兩個 bucket 覆寫。**

### 4-2 面板層(這才是問題)

`build_realbody_scores._score_stock()` 只取了 8 個欄位,**沒有取 `dyn_weight` 與 `regime`** ——
而 `core/score_store.COLUMNS` 明明有這兩欄(`:59`)。所以:

> **面板存了結果,沒存產生結果的狀態。殘差只能反推,不能對帳。**

### 4-3 殘差實測(ADV≥100萬,259,652 列)

殘差 = `real_composite − Σw·face`(靜態 balanced 權重,直接用面板存的五面分):

| | |
|---|---|
| \|殘差\| ≤ 0.01 | **59.74%** ← 只有六成能完全對上 |
| \|殘差\| > 0.5 | 23.23% |
| \|殘差\| > 2.0 | 10.38% |
| \|殘差\| > 5.0 | **3.88%** |
| 中位 / 平均 | −0.001 / −0.242 |
| max / min | **+17.87 / −22.99** |

用三組 regime 乘數各自重算、逐列取最貼近者(反推):

```
全期:{'neutral': 0.619, 'bull': 0.288, 'bear': 0.093}
2005–2018:neutral ~0.90–0.95(與 4-3 的「沒資料的 neutral」一致)
2022      :bear 0.74     2024:bull 0.94
```

**這個反推與 `classify_regime()` 獨立重算的結果高度吻合**(2022 bear 0.75、2024 bull 1.0),
所以殘差的主成分確實是 regime 層;剩下的是 dyn_weight 與兩個 bucket 覆寫。

### 4-4 對既有結論的影響

`現況盤點_2026-07-29.md` §L4 體檢新發現第 3 點寫「殘差 16% 的列 >1 分」——

### 5-2 名目權重 vs 有效權重(**五面未標準化就直接加權平均**)

`advisor.advise()` 的 `composite = Σ w·bucket / Σw`,bucket 是原始 0–100 分,
**沒有 z-score、沒有百分位化**。所以「分得越開的面,實際主導排序的力道越大」:

| 面 | 名目 w | 月內 std | w×std | **有效權重** | 與綜合分 rank corr |
|---|---|---|---|---|---|
| 基本面 | 0.31 | 15.00 | 4.650 | **0.24** | 0.543 |
| 估值 | **0.08** | 29.04 | 2.323 | **0.12** | 0.208 |
| 技術 | 0.19 | 21.21 | 4.031 | **0.21** | 0.609 |
| 動能 | 0.27 | 15.79 | 4.263 | **0.22** | 0.635 |
| 籌碼 | 0.15 | 26.74 | 4.011 | **0.21** | 0.527 |

**五個面的有效權重被壓成 0.12–0.24 的一團**,名目上 0.31 : 0.08(近 4 倍差距)在有效層只剩 2 倍。
兩個 IC 顯著為負的面(技術 0.21 + 籌碼 0.21 = **0.42**)實際佔比高於名目 0.34。
與綜合分相關最高的是**技術(0.609)與動能(0.635)** —— 排序其實由這兩個面主導。

> 這解釋了記憶中「綜合分 0.61 的權重壓在無正貢獻的維度上」那條結論的機制:
> **問題不在權重數字,在於加權前沒有統一量尺。**

### 5-3 缺值語意 —— **同一個引擎裡三種相反的處置**

| 欄位 | 缺值處置(`build_pit_stockdata`) | 進到分數 | 判定 |
|---|---|---|---|
| `pe_vs_industry` | 缺 PE → 填 **10.0** | bounds lower=30/upper=10 → **100 分(最便宜)** | ❌ 缺值 = **最好分**,佔 f_fund 的 0.20 |
| `debt_to_asset` | 無資產負債表 → 停在初值 **0.0** | bounds 60→0 / 30→100,外插後 clip → **100 分** | ❌ 缺值 = **最好分** |
| `roe` / `net_margin` / `gross_margin` | 無損益表 → 停在初值 **0.0** | 分別 → 0 / 0 / 0 分 | ❌ 缺值 = **最差分** |
| `current_ratio` | 無資產負債表 → 停在初值 **100.0** | bounds 100→0 → **0 分** | ❌ 缺值 = 最差分 |
| `eps_cagr` | 缺 → 填 **0.0** | bounds 0→0 / 20→100 → **0 分** | ❌ 缺值 = 最差分,且因「有值」而計入 growth 平均 |
| `roe` 等傳 `None` 的情況 | `_avg_present()` 只對有值取平均;整組皆缺 → 50 | 中性 | ✅ 正確 |
| 估值整支資料不足 | `valuation_score = 0.0`,advisor 用 **50** | 合成中性、面板存 0 | ❌ **面板值 ≠ 合成用值** |
| 籌碼 washout | bucket = `min(100, max(whale,60)+5)` | 面板存**未加成**原始分 | ❌ **面板值 ≠ 合成用值** |

**關鍵**:`build_pit_stockdata` 把「沒資料」寫成了**具體數值**(0.0 / 10.0 / 100.0),
下游 `_avg_present()` 的「只對有值取平均」保護就**失效了** —— 它看到的是有值。
`FundamentalEngine` 設計上是有中性化機制的,但被上游的預設填值繞過。

**實測(直接餵「三大財報全缺 + 無 PE」的預設值給 `FundamentalEngine.evaluate()`)**:

```
子分數: roe 0.0  net_margin 0.0  gross_margin 0.0  eps_cagr 0.0  asset_turnover 0.0
        debt_to_asset 100.0  current_ratio 0.0  pe_vs_industry 100.0
組分數: profitability 0.0   growth 0.0   safety 50.0   valuation 100.0
total_score = 32.5    is_passed = True        ← 硬門檻照樣放行
(若月營收在、rev_cagr=10 → total_score = 41.88)
```

**這比「缺資料拿滿分」更難抓**:兩個方向相反的錯(獲利性 0 分 vs 負債比/估值 100 分)
**互相抵銷**,產出 32.5 / 41.9 這種「看起來很正常的中低分」,而全 panel 的 f_fund 中位是 46.6。
→ 缺財報的 stock-month **不會**在分布上露出馬腳,只會安靜地佔住排序中段。
而且 `is_passed = True`,基本面硬門檻完全沒攔到它。
