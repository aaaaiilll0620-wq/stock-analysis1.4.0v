## 2. 七層架構

> **修正(第二輪,2026-08-05)**:第一輪把 L5 畫在 L4 之後,等於「新倉決策做完才處理既有部位
> 退出」,時序錯誤。且 L6 內部混合了「個股事件」與「市場層級風控」兩種完全不同權限範圍的
> 輸入,也需要拆開。以下重寫為「L4 為唯一最終統整器,L5 與 L3 同一決策時點並行輸入」+
> 「L6 拆分為 L6a/L6b 兩個不互相越權的子介面」。

### 2.0 分層邏輯:L4 拆為 L4a 決策 / L4b 執行(不增加第八層)

> **修正(第三輪,2026-08-05)**:第二輪把「L4 裁決」與「`PositionState` 正式轉移」綁在一起,
> 與 §3.3「部位狀態由成交事件驅動(成交回報),不是判斷」直接矛盾——**決策**(要不要買/賣)
> 與**成交**(買/賣是否真的發生)是兩件事,合併會讓「L4 決定退出」被誤讀成「退出已經生效」。
> 在不增加第八層的前提下,把 L4 拆成兩個子介面。

```text
L1 選股資格／排序 → L3 原始進場候選 ┐
L5 既有部位的退出／續抱提案         ├→ L4a 投組決策(OrderIntent) → L4b 執行帳本(成交/未成交) → L7 呈現
L2 族群限制 + L6a/L6b 事件與市場限制 ┘
```

| 子介面 | 職責 | 輸入 | 輸出 | 可改寫 `PositionState`? |
|---|---|---|---|---|
| **L4a PortfolioDecisionEngine** | 統整 L3 候選、L5 提案、L2/L6 限制,產生**意圖**,不是結果 | L3 候選、L5 提案(`hold`/`exit`,見 §6.2 修正)、L2 的曝險/現金/集中度限制、L6b 的曝險/現金/新倉限制、投組限制(§7) | `OrderIntent`(目標權重/交易意圖) | **不能** |
| **L4b ExecutionLedger** | 依 Phase 2 凍結的 T+1、價格區間、跳空、滑價、交易成本、零股限制、部分成交/未成交規則,模擬 `OrderIntent` 的實際執行 | `OrderIntent`(來自 L4a)、Phase 2 凍結的執行規則(§9) | 成交回報(`filled`/`partial`/`cancelled`/`rejected`) | **只有**成交或可驗證的 execution receipt 才能更新 `PositionState`、成本、現金、持股 |

**執行狀態鏈**(至少區分,避免把「意圖」「決策」「結果」混成一個狀態):

```text
candidate/proposal → OrderIntent → submitted/pending → partial/filled/cancelled/rejected
```

- **`PositionState` 只在收到 `partial`/`filled` 或可驗證的 execution receipt 時才轉移**,
  不在 L4a 產生 `OrderIntent` 的當下轉移——這才與 §3.3「部位狀態由交易事件驅動」一致。
- **`pending_exit` 重新定位為「執行狀態」**(L4b 的輸出,表示 `OrderIntent` 已送出但受
  §7 流動性 0.1% ADV20 限制須分批出清、尚未完全成交),**不是** L5 的 `exit` 提案本身——
  L5 只送 `hold`/`exit` 兩種提案(見 §6.2 修正),`pending_exit` 由 **L4b** 在執行層產生,
  不與 L5 的提案混為同一層。
- **強制退出不得被 L4a 否決**:強制退出(§7 判斷優先序第 1 級)可突破換手上限,**L4a 不得
  因換手率、產業集中度上限或「沒有替代股可補位」而否決這筆賣出的 `OrderIntent`**;若市場
  流動性不足導致無法立即成交,**只能由 L4b** 記為 `pending`/`partial`,並保留該筆未平倉
  風險在報告中揭露,不得因執行困難就在決策層假裝這筆退出不存在。
- **無券商 API 不代表可以省略 execution ledger**:V2 不對接券商(§1.2),但**回測本身仍需要
  L4b 模擬執行**——否則所有報酬/成本/滑價都建立在「全部立即以決策價成交」的失真假設上。
- **`Z1-R` 仍由 L3 產生**(進場訊號,見 §6.1),但**輸入不只是 L1 排名與價格結構**——
  `Z1-R` 額外需要一份只讀的 `ReentryContext`(第四輪修正,2026-08-05,見 §6.1.1),否則
  無法判斷「前次交易是否真的成交退出、退出時間、舊交易風險結構」。其重新進場**仍須經 L4a
  裁決產生 `OrderIntent`,再經 L4b 成交後才正式生效**,不因為是「收復」就跳過執行層;
  若該股當時有效的 L6a `block_entry_or_reentry_flag`,**L4a 否決該筆 `OrderIntent`**,
  但**L3 產生的原始 `Z1-R` 候選本身不受影響、不得被靜默刪除**(見 §6.1.1、§6.3),
  以維持「訊號本體」與「事件限制」可分開驗證。
- **`E1-R` 只是一個實驗組態標籤**(`E1` 退出政策 + `Z1-R` 重新進場的組合名稱),**不是**
  L5 的政策、不是訊號、也不是獨立的狀態轉移器。**清除第二輪不精確的表述**:「`E0`/`E1`/`E1-R`
  都是 L5 產生提案的政策」是錯的——**L5 只有 `E0` 或 `E1` 兩種退出政策**,`E1-R` 是組態標籤,
  不是第三種政策(見 §6.2 修正)。**`E1-R` 不代表所有 `E1` 退出都必然允許 `Z1-R` 重進**——
  是否合格由 §6.1.1 凍結的 `ReentryContext` 資格規則判定(見問題 3 修正)。

### 2.1 L6 拆分:L6a StockEventAux / L6b MarketRiskOverlay

原版 L6「消息與市場輔助」混合了「個股層級事件」與「市場層級風控」兩種權限範圍不同的輸入,
拆為兩個互不越權的子介面(**仍算七層之一,只是 L6 內部有兩個子介面**):

| 子介面 | 輸入 | 唯一允許輸出 | 明確禁止 |
|---|---|---|---|
| **L6a StockEventAux** | 具 PIT 時間戳的**個股**重大事件與其嚴重度 | **修正(第四輪,2026-08-05):兩種輸出、兩個不同目的地**——①`forced_exit_flag`(強制出場旗標)**→ L5**,使既有部位產生強制退出提案;②`block_entry_or_reentry_flag`(新倉/重進硬否決旗標,**取代第二輪誤標的 `block_reentry_flag`**)**→ L4a**,阻止任何新倉或重進 `OrderIntent`(不論候選來自 `Z1-P`/`Z1-B`/`Z1-R` 哪一個) | **不得**改寫 L1、L3 的原始訊號本身、`TrendState`、`PositionState`;**不得**對 L4a 下曝險/現金/新倉限制(那是 L6b 的專屬權限);L4a 收到否決旗標時**必須明確記錄「因事件旗標否決」**,不得讓 L3 候選被靜默刪除(見 §6.3) |
| **L6b MarketRiskOverlay** | 市場狀態資料 | 對 **L4a** 輸出總曝險上限、現金下限、新倉/加碼限制(權限不變) | 不得向 L5 或 L4a 發送個股層級的退出/否決旗標;不得改寫 L1、L3、`TrendState`、`PositionState` |

> **問題根源(第四輪修正說明)**:第二輪把 `block_reentry_flag` 路由到 L5,但 **L5 只處理
> 既有部位的退出提案**,無法阻止 L3 的新進場候選經 L4a 產生 `OrderIntent`——一個已經觸發
> 停損、正在被 L6a 事件旗標禁止重進的股票,若旗標送到 L5,L5 根本沒有機制能否決 L3 端的
> `Z1-R` 候選。改送 L4a 才能在「是否產生 `OrderIntent`」這一步真正卡住。

- **事件等級、來源、可用時間與失敗語義仍為 CANDIDATE/UNRESOLVED**(見 §11 U6),不得自行定門檻。
- **異常價格、初始停損、trailing、跳空屬 L5 的職責範圍**(既有部位依價格結構與部位規則
  產生 `hold`/`exit` 提案的依據);**`pending_exit` 屬 L4b 的執行狀態**(見 §2.0),兩者
  皆**不屬於 L6b**——L6b 只處理市場層級的曝險/現金/新倉限制,不產生任何個股層級的退出
  相關提案或執行狀態。

## 3. 三套獨立狀態機

任務文件明確要求「市場狀態、族群狀態、個股趨勢狀態/部位狀態」三者分離,且
「不得把停損等同於看壞」。以下逐一定義狀態空間與合法轉移,狀態機定義本身屬
**CANDIDATE**(尚待預註冊與回測驗證轉移規則的實際效果),但分離原則屬 **FROZEN**
(任務文件已明定)。

### 3.1 市場狀態 MarketState

- 目的:只管理**曝險、現金及新增風險**,不得直接改寫個股評分排序,也不得對個股下退出旗標
  (對應 **L6b→L4a** 的單向輸入,見 §2.1;個股層級的事件旗標由 **L6a→L5** 另外處理,兩者不得
  混用同一輸出管道)。
- 現有可參考起點:`core/regime_exposure.py` 的曝險階梯(3/3、2/3、1/3、0,UP/DOWN 各 3 日遲滯),
  但其增益尚未依 `docs/架構分離_StrategyBodyVsOverlay.md` §4 的 **P-Overlay-C** 走完預註冊驗證,
  V2 設計**只能引用其介面(輸入 0050 或全市場指數、輸出曝險比例),不得引用其「已驗證降低 MDD」
  的結論**。
- 候選狀態集合(CANDIDATE,窗長/門檻不凍結):看多 / 中性 / 看空,或延伸為更細的曝險階梯。

### 3.2 族群狀態 GroupState

- 狀態集合(任務文件已定案,**FROZEN** 這五個標籤名稱,**CANDIDATE** 判定邏輯):
  `萌芽 → 擴散 → 主升 → 過熱 → 退潮`。
- 允許逆向轉移(例如 主升 → 擴散,族群降溫但未到過熱)與跳級轉移(例如 擴散 → 退潮,
  題材急殺),**不得預設只能單向前進**。
- 三種群組分類(官方產業/題材/資料驅動相關群組,見 §5)**各自維護一套族群狀態**,
  不得合併成單一標籤(否則官方產業裡的非題材成分會被題材熱度污染)。

### 3.3 個股趨勢狀態 / 部位狀態(TrendState / PositionState,必須分離為兩個欄位)

| 狀態機 | 狀態集合(CANDIDATE) | 說明 |
|---|---|---|
| **PositionState**(部位) | `無持有 → 建倉中 → 持有 → 減碼中 → 已停損 → 觀察中(停損後)` | 描述「現在手上有沒有這檔股票、部位大小」,由交易事件驅動(成交回報),不是判斷 |
| **TrendState**(趨勢) | `上升 → 整理 → 轉弱 → 失效` | 描述「這檔股票的價格結構評估」,由價格/量能資料驅動,與是否持有無關 |

**修正(第三輪,2026-08-05)**:`PositionState` **只由交易事件(成交回報)驅動**——具體來說是
**L4b 的 `filled`/`partial` 成交回報或可驗證的 execution receipt**(見 §2.0),**不是**
L4a 的決策(`OrderIntent`)、不是 L5 的提案、也不是任何「判斷」直接觸發。以下所有轉移都
隱含「已由 L4b 產生對應成交回報」這個前提,不再寫成「由 L4 裁決後正式化」(該表述與本節
矛盾,已刪除)。

**合法轉移範例(避免停損=看壞的誤植)**:

- `PositionState: 持有 → 已停損` 在 L4b 回報停損單 `filled` 時觸發,`TrendState` **不強制**
  同步變成 `轉弱`或`失效`——停損可能單純是價格跌破移動停利點,趨勢判斷仍可維持 `整理`,
  此時股票進入 §8 網頁分類的「停損後觀察」而非「趨勢失效」。
- `TrendState: 整理 → 失效` 才是「不追價」/「趨勢失效」分類的觸發條件,與部位是否已出場無關,
  且 `TrendState` 本身不經過 L4b(它是價格結構判斷,不是交易事件,見 §3.3 表格)。
- `PositionState: 已停損 → 觀察中` 後,若後續出現 `Z1-R`(停損後重新進場訊號,L3 產生,
  需 `ReentryContext` 資格,見 §6.1.1),經 **L4a** 裁決產生 `OrderIntent`、**再經 L4b 成交**
  後才可能重新進入 `建倉中`;`Z1-R` 命中本身不代表自動建倉,只是把該股票放進「收復候選」
  名單。**若該股當時有效的 L6a `block_entry_or_reentry_flag`,L4a 否決此次重進**
  (第四輪修正,見 §2.1),但 `PositionState` 仍停留在 `觀察中`,不因否決而變成其他狀態。
- 市場狀態/族群狀態轉弱,**只能**調整 **L4a** 的曝險與新增部位的資格(例如暫停新倉),
  **不得**直接把已持有個股的 `TrendState` 或 `PositionState` 改寫(對應任務文件的硬性禁止)。

### 3.4 決策時鐘 DecisionClock(新增,必修 3,2026-08-05)

> 目前「月頻正式選股/再平衡;週頻複核;日頻進出場」只有一句話,**不足以讓 L4a 重現
> 某一天的決策**——沒有明確的凍結/失效時點,同一組資料在不同重跑時間點可能得到不同結果。
> 本節**只列介面與未決項,不自行定參數**,具體數值列為 §11 **UNRESOLVED U7**,
> **Phase 2 前必須凍結**。

**待凍結的介面範圍**:

| 頻率 | 待決問題 |
|---|---|
| 月頻 | 正式候選池/排名**何時凍結**、凍結後**有效到何時**(下次月頻更新前是否可能被更早失效) |
| 週頻 | 哪些欄位重算(順位?基本面?風險?);週頻複核**能否正常換股**,或只能調整風險旗標/觀察狀態,不得變更目標持股 |
| 日頻 | 進場區間、停損、重大事件、`pending` 訂單**何時更新**;是否每個交易日收盤後都重算,或僅在特定觸發條件下 |

**每個訊號(L1 排序、L2 族群狀態、L3 候選、L5 提案、L4a `OrderIntent`)必須帶有**:

- `as_of`:訊號描述的是哪個時點的世界狀態
- `generated_at`:訊號實際被計算出來的時間
- `valid_from` / `valid_until`:訊號的有效區間
- `source_snapshot_hash`:產生此訊號所用的資料快照 hash(確保可重現、可稽核)

**衝突處理(CANDIDATE,待 Phase 2 凍結)**:

- **L4a 在同一決策時點遇到月/週/日訊號衝突時的優先序**——例如月頻排名尚未過期,但日頻
  停損訊號要求立即出場,兩者如何排序、是否日頻永遠可以覆蓋月頻的「持有」判斷——待定案。
- **T 收盤訊號最早 T+1 執行**(呼應 §9 執行時點規則),**不得讓月頻排名被日後資料回填**——
  例如月底計算的排名,不得在月中因為財報延遲公告而事後改變當月已經生效的排名。

**與其他章節的關係**:本節定義的 `as_of`/`generated_at`/`valid_from`/`valid_until`/
`source_snapshot_hash` 欄位適用於 §2 各層輸出、§6 的候選/提案、§10 Phase 2 的凍結文件
格式,是跨層的共同介面,不是獨立的第八層。

### 5.1 重疊與衝突處理原則

- 一檔股票可同時屬於一個官方產業、零至多個題材標籤、以及依統計方式浮動歸屬的資料驅動群組——
  **三者不互斥**。
- 集中度計算(§7)以**官方產業**為唯一硬上限依據(任務文件:「產業 50% 是現有硬上限」),
  題材與資料驅動群組的上限與門檻**皆為 UNRESOLVED**(見 §11),Phase 0 不代使用者定案。
- 衝突處理原則(CANDIDATE,需驗證):當題材標籤與資料驅動相關群組對同一批股票給出矛盾的
  族群狀態(例如題材判定「主升」但統計相關性顯示該批股票其實分屬兩個不相關驅動因子),
  **不得自動平均或取多數決**,應在 L2 輸出中同時保留兩個標籤與衝突旗標,交給 L4a/L7 呈現層
  分開顯示,不得在資料層悄悄合併(呼應「不得把市場/族群燈號與個股分數直接平均」)。
- 「同一行情事件中的多檔股票不得當成互相獨立的證據」——這條規則主要透過**資料驅動相關群組**
  在統計上偵測。**修正(必修 6,2026-08-05)**:「高相關個股簇視為一個證據單位」**不是**
  Phase 0 就能宣稱的正確方法,只能列為**待預註冊的群聚推論候選**(例如 cluster-aware
  inference、有效樣本數折減等),具體聚類方法、門檻與統計處理方式屬 UNRESOLVED(見 §11 U5、C9)。
  Phase 0 不得直接假設「簡單合併成一筆觀測」就是正確做法。

## 6. 進場與退出候選:責任邊界

> 以下 `Z1-*` / `E0` / `E1` / `E1-R` 命名沿用任務文件定義,**目前系統程式碼中沒有對應實作**,
> 全部是本輪新提出的候選規格,狀態逐項標示。**視為全新研究模組(D4,2026-08-05 使用者確認)**:
> 可重用既有資料存取工具(價量、財報等),但**不繼承** `core/backtest` 現有停損邏輯的語義。

#### 6.1.1 `ReentryContext`(`Z1-R` 專屬只讀輸入,第四輪新增,2026-08-05)

> **問題**:`Z1-R` 不可能只靠 L1 排名與價格結構判定——它必須知道「前次交易是否真的因
> 退出政策成交離場、退出時間、舊交易的風險結構」,否則無從定義「重新進場」相對於什麼
> 基準。以下只列候選欄位與資格前提,**不自行定參數**,具體 schema 列為 §11
> **UNRESOLVED U10**。

**候選欄位(CANDIDATE,待 Phase 2 凍結)**:

- 前次 `trade_id`、退出政策(`E0`/`E1`)與退出原因;
- **L4b** 實際退出成交時間/價格/execution receipt(見 §2.0——必須是已確認成交,不是
  L4a 的 `OrderIntent`);
- 舊交易的 `P0`/`S0`/`R0` 與最後有效停損;
- 當前 `PositionState` 及是否仍在重進觀察期;
- 未解除的個股事件禁止旗標(L6a `block_entry_or_reentry_flag`,見 §2.1)。

**建立 `ReentryContext` 的前提(FROZEN 原則,細節 UNRESOLVED)**:

- **只有「前次退出已由 L4b 確認成交」**(不是 L4a 決策、不是待成交的 `OrderIntent`)
  **且退出原因符合凍結的 `Z1-R` 資格規則**,才能建立 `ReentryContext`。
- 排名淘汰、基本面惡化、重大事件強制退出**是否永久或限期禁止重進**,留給 §11 **U6**
  (L6a 事件語義)與 `Z1-R` 專屬預註冊決定,**Phase 0 不得自行決定**。

**UNRESOLVED U10**:`ReentryContext` 的具體欄位 schema、可接受的退出原因清單、觀察期限
與失效條件,均待 Phase 2 前凍結,本檔不代為選擇。

### 6.2 退出候選(L5 只有兩種退出政策;`E1-R` 是組態標籤,不是第三種政策)

> **修正(第三輪,2026-08-05)**:清除第二輪「`E0`/`E1`/`E1-R` 都是 L5 產生提案的政策」的
> 不精確表述。**L5 只有 `E0` 或 `E1` 兩種退出政策**,用來判定 `hold`/`exit` 提案(見 §2.0、

> `PositionState`——不是 L5 自己直接執行的最終訊號。`pending_exit` 不是 L5 的提案類型,

| 代號 | 定義 | 責任範圍 | 狀態 |

| `E0` | 無固定移動停利 | **不是**只靠初始停損產生 `exit` 提案——`E0` 仍可能因結構轉弱(`TrendState`)、排名跌出候選(L1 資格/排名狀態)、基本面惡化(PIT 基本面惡化旗標)或 L6a `forced_exit_flag` 而產生 `exit` 提案;與 `E1` 的差異**只在於不使用固定停利或 ATR trailing 這類價格距離規則**,不代表退出條件比較少 | CANDIDATE(作為對照組) |

價位微調。

### 6.3 責任邊界(與 §3 狀態機、§2.0 L4a/L4b 架構的關係)

- **進場候選(`Z1-*`,L3 產生)** 只是候選,**不得**跳過 L4a 直接下單。L4a 依 §7 投組限制
  (現金、集中度、單股上限)、L6a 的 `block_entry_or_reentry_flag`(個股層級硬否決,見 §2.1)
  與同批 L5 提案一起裁決,產生 `OrderIntent`;`PositionState` 是否真的從 `無持有` 轉移到
  `建倉中`,**要等 L4b 回報成交(`filled`/`partial`)才發生**。**L4a 對 L6a 否決的候選必須
  明確記錄「因事件旗標否決」**(第四輪修正),不得靜默丟棄——`L3` 產生的原始訊號與 L6a
  的事件限制須保持可分開驗證,不能因為否決就讓訊號本體的紀錄消失。
- **退出提案(`E0`/`E1` 政策下,L5 產生的 `hold`/`exit` 提案)**,**不得**自己直接把
  `PositionState` 改成 `已停損`/`觀察中`——由 **L4a** 依提案裁決產生 `OrderIntent`,
  **L4b** 回報成交後才正式轉移。裁決結果**不得**連動把 `TrendState` 改寫(見 §3.3,
  停損不等於看壞)。**強制退出的 `OrderIntent` 不得被 L4a 因換手/集中度/無替代股否決**
  (見 §2.0、§7);若 L4b 無法立即成交,以 `pending`/`partial` 執行狀態保留風險揭露。
- L3 的候選與 L5 的提案**在同一決策時點一起送進 L4a**(見 §2.0 圖示),L4a 對兩者一視同仁地
  套用 §7 優先順序,不因為訊號來源是「新倉」或「既有部位」而有隱性優先權。
- `+1R` 只開啟加碼資格(任務文件明定),**不自動把停損移到成本**;不得對虧損部位攤平;
  加碼本身視為建立一筆新的子結構(新的進場記錄,由 L3 產生候選、經 L4a 裁決、L4b 成交後
  才生效),必須重算共同停損下的計畫損益,這條規則對 `Z1-P`/`Z1-B`/`Z1-R` 一體適用
  (加碼的完整語義見 §7.2)。

## 7. 投組限制優先順序

任務文件已定案的硬限制(**FROZEN**,數值不得自行調整):

| 限制 | 數值 |
|---|---|
| 持股數 | 1–10 檔,候選最多 15 檔,等權 |
| 初始股票部位 / 加碼預備金 | 90% / 10%,允許持有現金 |
| 單股上限 | 基礎 30%,最高 35% |
| 單一產業硬上限 | 50%(以官方產業分類計算,見 §5) |
| 流動性 | `ADV20 >= NT$10,000,000`;單次預計交易金額 `<= 0.1% ADV20` |
| 頻率 | 月頻正式選股/再平衡;週頻複核順位、基本面、風險;日頻進出場/停損/異常價格與消息;重大事件允許提前退出 |
| 換手 | 正常單向月換手率目標/上限 20%;強制退出可突破,但正常換手、強制換手、總換手、交易成本須分開揭露 |

### 7.1 判斷優先順序(CANDIDATE,規則本身待驗證,但優先序邏輯依任務文件精神訂定)

當多個限制同時觸發、彼此衝突時,建議判斷順序如下(由高到低,高優先者先滿足):

1. **強制退出 / 停損**(風控層,日頻):異常價格、重大事件、觸發停損 —— 不受換手率上限、
   單股/產業上限約束,可突破正常換手率上限,但需完整揭露(見 §9)。**L4a 不得因換手率、
   產業集中度上限或「沒有替代股可補位」否決這筆退出的 `OrderIntent`**(見 §2.0、§6.3);
   若 L4b 無法立即成交,以 `pending`/`partial` 執行狀態保留風險,不得在決策層假裝不存在。
2. **單股 / 產業集中度硬上限**(35% 個股、50% 產業):任何新增部位若會使某股或某產業超過
   硬上限,直接否決該筆加碼/新倉,即使選股或進場訊號成立。
3. **流動性限制**(ADV20 門檻、單次 0.1% ADV20):候選若不滿足流動性門檻,不得進入候選池,
   優先序高於排名本身。
4. **現金水位與加碼預備金**:10% 加碼預備金僅在 `+1R` 資格開啟後可動用,不得挪用於新標的
   首次建倉(避免稀釋既有部位的加碼資格)。
5. **正常月頻再平衡與換手率目標**:在以上規則都滿足後,才依月頻排序結果調整持股至目標
   換手率 20% 以內。

此優先序本身屬 CANDIDATE,需在 Phase 2 新預註冊中連同投組建構演算法一起凍結與驗證。

### 7.2 加碼預備金分配語義(必修 4,2026-08-05)

> 草案先前只寫「加碼預備金 10%」的總量,漏掉已討論的個股隔離語義,以下補齊。

**FROZEN(任務文件既有決定,本節只是展開)**:

- **不得對虧損部位攤平**。
- `+1R` **只開啟加碼資格**,**不自動把停損移到成本**(見 F8)。
- 加碼須滿足:①使用與原始進場**相同模式**建立**新結構**(新的進場記錄,見 §6.3),
  具體依母交易的原始進場模式而定:
  - **`Z1-P` 母交易**:加碼候選仍須**新 `Z1-P` 結構**。
  - **`Z1-B` 母交易**:加碼候選仍須**新 `Z1-B` 結構**。
  - **`Z1-R` 母交易**:**依 U11,暫不定義加碼模式**(見下方 UNRESOLVED U11)——
    **未解決前不得把「`Z1-R` 母交易可依 `Z1-R` 加碼」寫成既定規則**。
  ②加碼價格**高於原平均成本**;③加碼後在**共同停損**下的計畫淨損益**不得低於 0**
  (即加碼不得讓整筆交易的最壞情境轉為虧損)。
- **10% 加碼預備金按合格持股分配為每檔獨立額度**,股票之間**不得互相挪用**(A 股沒用完的
  額度不能挪給 B 股加碼);**每檔股票每月最多加碼一次**。

**UNRESOLVED U8(2026-08-05 新增,不得自行選擇)**:

- 「每檔獨立額度」的**分母 N** 如何定義——候選:①月初目標持股數;②當月實際持股數
  (可能因流動性/集中度限制小於目標數);③其他定義(例如排除當月已達加碼上限的持股後
  重新分攤)。三者在持股數低於目標上限時會給出不同的每檔配額,**Phase 2 前必須凍結**,
  本檔不代為選擇。

**90% 是目標上限,不是必須填滿(明確語義)**:

- 初始股票部位 90%(F2)是**目標上限**,不是強制要求。若合格候選數 N 太少,或單股 35%
  硬上限、產業 50% 硬上限使 90% 無法被合規配置,**剩餘部位維持現金**,**不得**為了湊滿
  90% 而突破 §7 的硬上限,也**不得**塞入不合格的股票充數。

## 8. 網頁資訊架構

都必須能回推成 `(PositionState, TrendState, MarketState/GroupState)` 的明確組合,
確保網頁呈現與底層狀態機邏輯一致,不會出現「畫面上寫著看好但底層趨勢已失效」的不一致。

> **修正(依 Codex 2026-08-04 審查)**:原版「值得持有」只看 `TrendState=上升`,「不追價」只看
> `整理`/`轉弱`,兩者都過度簡化。以下改列**必要判斷維度**(仍為 CANDIDATE,具體門檻待 Phase 2
> 凍結),不是單一欄位就能決定分類。
>
> **補記(第三輪修正,2026-08-05)**:下表的 `PositionState` 一律指 **L4b 成交回報(`filled`/
> `partial`)或可驗證 execution receipt 後正式化**的狀態(見 §2.0、§3.3),**不是** L4a
> 的 `OrderIntent`、也不是 L3 候選或 L5 提案本身;尚未成交的候選/提案/`OrderIntent`
> 不進入本表的分類邏輯。

| 分區 | 對應狀態(CANDIDATE 組合,判斷維度待 Phase 2 凍結) |
|---|---|
| 值得持有 | `TrendState=上升` **且** L1 評分達候選池門檻(§7)**且** 資料完整性檢查通過(§9 PIT/缺值檢查,不得因資料缺口誤判)**且** 基本面未觸發淘汰旗標**且** 無未平倉的 L6a `forced_exit_flag`;不論 `PositionState` 是否已持有 |
| 現在可買 | `值得持有` ∩ 進場候選命中(`Z1-P`/`Z1-B`)∩ 通過 §7 投組限制檢查(集中度、流動性、現金水位)∩ **無有效的 L6a `block_entry_or_reentry_flag`**(第四輪修正——否則 L4a 會否決該候選的 `OrderIntent`) |
| 持有中 | `PositionState ∈ {建倉中, 持有, 減碼中}` |
| 停損後觀察 | `PositionState=觀察中`(已停損)且 `TrendState ≠ 失效` —— 明確區分「出場了但沒看壞」 |
| 收復候選 | `PositionState=觀察中` 且命中 `Z1-R`(需 `ReentryContext` 資格,見 §6.1.1;`E1-R` 情境下的重新進場判定即為同一個 `Z1-R`,不另外產生訊號)。**若同時有效的 L6a `block_entry_or_reentry_flag` 導致 L4a 否決**(第四輪修正),仍顯示為「收復候選(已否決)」而非從清單移除——保留訊號本體可見性,不與事件限制混為一談 |

| 趨勢失效 | `TrendState=失效`,不論持有與否,提示應避免新建部位 |

**呈現層原則**:偏空判斷(§1.2)可在個股頁顯示,但不得出現在「可買」相關分區;
權證相關資訊(若顯示)須與正式股票策略績效分開呈現區塊,不得混合計算或並列成同一組合報酬。

- **Blocker(D3,2026-08-05 使用者確認)**:**官方產業分類 PIT 化列為本階段正式驗證的

  不得以「先假設有資料」跳過。

### Phase 2 — 規格凍結

- **輸入**:Phase 1 覆蓋率報告 + 使用者對 §11 UNRESOLVED 項目的裁決,**含 U7 DecisionClock
  的具體重算時點/有效期/衝突規則**(§3.4)。
- **輸出**:每一層(L2–L5)各自的 `docs/預註冊_*.md`,凍結窗長、門檻、狀態轉移規則、
  搜尋空間,**並寫死 Train / Validation / walk-forward 三段樣本期的切點日期**
  (不得等看過某一段結果後才決定下一段的起始日)。**L4b 執行模擬規則(必修 1,見 §9)**
  ——T+1、可成交價格區間、跳空、滑價、成本、零股、部分成交規則——**須與其他規格一起凍結**,
  不得留到 Phase 3 才決定。
- **前置條件**:**U7 DecisionClock 必須先於本階段完成凍結**(見 §3.4、§11 U7),否則
  Phase 2 的窗長/門檻凍結無法保證可重現(不知道訊號在哪個時點失效)。
- **必修 5:兩種合法凍結路徑(2026-08-05)** ——Phase 2 不一定能同時凍結「搜尋空間」與
  「最後選中的參數」,每一層須明確採用下列其中一種路徑,並在預註冊文件中聲明採用哪一種:

  | 路徑 | 定義 |
  |---|---|
  | **Policy-fixed** | Phase 2 直接凍結**唯一參數**,Phase 4(Train)只做診斷,不做參數搜尋 |
  | **Train-selected** | Phase 2 凍結**有限候選 grid**、搜尋數上限、選擇準則、tie rule、
    seed、樣本切點;Phase 4 只能依此規則在 Train 期選出唯一規格,見下方 Phase 4 的
    `TRAIN_SELECTION_MANIFEST` 要求 |

- **停止條件**:所有必須新預註冊的項目(呼應 §9 與研究紀律 §2)完成凍結文件並經審查,
  且每一層已聲明採用 Policy-fixed 或 Train-selected。
- **Fail-closed**:任何一層規格未凍結前,不得進入 Phase 3。

### Phase 3 — runner / tests

- **輸入**:Phase 2 凍結規格。
- **輸出**:各層 runner 程式骨架 + 單元測試。**必須精確實作 Phase 2 已凍結的內容**——
  依 Phase 2 聲明的路徑,**Policy-fixed** 層須精確實作**唯一參數**;**Train-selected** 層
  須實作**完整候選 grid + 決定性選擇規則**(不得自行補值、不得用近似值頂替未凍結的部分)。
  若某功能的規格確實尚未凍結,只能以明確標記為 stub 的形式存在,且不得進入任何判定路徑。
- **停止條件**:所有狀態轉移(§3)、責任邊界(§6.3)、優先順序(§7.1)皆有對應測試案例,
  且測試案例直接對應 Phase 2 凍結文件中的參數值或 grid+選擇規則(而非另行假設的值)。
  **另須有專門測試案例驗證 L4a/L4b 分離**(必修 1):`OrderIntent` 產生時 `PositionState`
  不得改變;只有模擬的 `filled`/`partial` 成交回報才能改變 `PositionState`;強制退出的
  `OrderIntent` 在測試中不得被 L4a 以換手/集中度理由否決。
- **Fail-closed**:任何測試失敗,或發現 runner 與 Phase 2 凍結文件不一致,即停止,
  不得跳過失敗測試進入下一階段。

### Phase 4 — Train

- **輸入**:Phase 3 runner + Train 期資料(切點見 Phase 2)。
- **輸出**:
  - **Policy-fixed** 層:in-sample 診斷報告(比照研究紀律「診斷可自由跑,但診斷不是結論」)。
  - **Train-selected** 層:in-sample 診斷報告 **+ 不可變的 `TRAIN_SELECTION_MANIFEST`**
    (必修 5),在開啟 Validation 前產生,至少記錄:
    1. 選中規格與全部參數;
    2. 候選全集與選擇規則(對應 Phase 2 凍結的 grid/準則/tie rule/seed);
    3. Train 資料截止日;
    4. 程式/設定/資料快照 hash;
    5. 產生時間與成功/失敗狀態。
- **停止條件**:完成 Train 期診斷報告(與 manifest,如適用),不得寫成結論句。
- **Fail-closed**:diagnostic 顯示規格有明顯資料洩漏(例如非 PIT 欄位混入)則整層打回
  Phase 2;Train-selected 層若無法產生完整 manifest,不得進入 Phase 5。

### Phase 5 — Validation

- **輸入**:Phase 4 結果(含 Train-selected 層的 manifest)+ Validation 期資料(與 Train 期
  不重疊,切點見 Phase 2)。
- **Validation 存取控制(必修 5,第三輪強化,2026-08-05)**:第二輪只檢查
  `TRAIN_SELECTION_MANIFEST` 時間戳,但**這只能證明「已記錄的讀取」發生在何時,不能單獨
  證明資料從未被提前看過**——**Phase 0 不宣稱它能完全證明盲性**。補列 Phase 2/4/5 的候選
  要求(具體 schema 與封存機制列為 **UNRESOLVED U9**,不得在 Phase 0 宣稱已完成):
  1. **Validation 資料入口必須由 guard 控制**,runner 不得繞過直接讀檔。
  2. **第一次開啟時留下 append-only access receipt**,至少含:manifest hash、程式 hash、
     資料 snapshot hash、時間、操作者/run id。
  3. **preflight 同時核對** `TRAIN_SELECTION_MANIFEST` **與** first-access receipt——
     manifest 缺失、receipt 缺失,或兩者時間順序不對,**直接 fail-closed**,不得繼續。
  4. 若事後發現**人工或其他未受控路徑曾提前讀取 Validation 資料**,**fail-closed**;
     後續處置(是否整層作廢、是否需要換一份未曝光的資料重測)**須在預註冊中事先定義**,
     不得臨時決定。
- **輸出**:對照 §9 三階基準的 Validation 期結果、第二條獨立實作對帳結果。
- **必修 4:`VALID_FAIL` 與 `INVALID` 的區分**(適用本階段全部判定):

  | 類別 | 定義 | 處置 |
  |---|---|---|
  | **`VALID_FAIL`** | 實作、資料血緣、PIT、第二實作對帳**全部有效**,但**未達凍結績效門檻** | **有效的否定結論**,必須保存並停止該候選;**不得**寫成「結果作廢」,**不得**回到 Phase 2 後在同一 Validation 期重新測試 |
  | **`INVALID`** | 資料洩漏、非 PIT、runner 與凍結規格不符、第二實作對帳失敗、必要欄位缺失等**完整性問題** | **不得下科學結論**,結果無效;依根因退回 Phase 1/2/3。修正後仍**不得**任意重用已揭露的 Validation 資料;後續處置須在預註冊中事先定義 |

- **停止條件**:每一層須在 Validation 期得到 `VALID_FAIL` 以外的結果(即通過凍結門檻)
  才可進入 Phase 6;`VALID_FAIL` 依上表處置並停止該候選,`INVALID` 依根因退回。
- **Fail-closed**:manifest 或 access receipt 檢查未過、判定為 `INVALID`,或偵測到未受控
  提前讀取,則退回對應階段;`VALID_FAIL` 不是 fail-closed 事件,是正常保存的否定結論。

### Phase 6 — Walk-forward

- **輸入**:Phase 5 通過結果(非 `VALID_FAIL`/`INVALID`)+ walk-forward OOS 期資料
  (與 Train、Validation 期皆不重疊,切點見 Phase 2)。
- **輸出**:walk-forward OOS 結果、第二條獨立實作對帳結果。
- **`VALID_FAIL`/`INVALID` 區分同 Phase 5,適用於 walk-forward 判定**。
- **停止條件**:與 Phase 5 相同邏輯應用在 OOS 期;`VALID_FAIL` 照登保存,`INVALID` 退回。
- **Fail-closed**:`INVALID` 則退回對應階段;**不得用 walk-forward 結果回頭調整 Validation
  或更早階段的任何規格**(呼應研究紀律單發射擊制),即使 walk-forward 結果是 `VALID_FAIL`
  也不例外。

### Phase 7 — 網頁整合

- **輸入**:Phase 6 通過的各層結果。
- **輸出**:§8 網頁資訊架構的實際實作,含分區邏輯與狀態機串接。
- **停止條件**:網頁呈現的每一分區可回溯到通過驗證的狀態組合。
- **Fail-closed**:任何一層尚未通過 Phase 6 驗證,其對應網頁分區須明確標示「未驗證/研究中」,
  不得以「先上線再補驗證」的方式呈現。
