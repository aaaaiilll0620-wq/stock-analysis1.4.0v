## 1. 目的與邊界

**目的**:把 dual100 每月算出來的「Top-48 名單」,變成「今天實際該買賣多少張」,
並追蹤「有沒有真的照這樣執行」。這是純工程,不改變、不重新驗證選股邏輯本身。

**回答的問題只有兩個**:
1. 給定目標名單、目前持倉、可用資金 → 今天該送出什麼單(L4a)?
2. 給定送出的單、當天實際市場資料 → 實際成交了什麼、帳本現在長怎樣(L4b)?

**不回答**(見 §8):要不要調整選股邏輯、要不要套 overlay、要不要放寬/收緊 ADV 門檻。

---

## 2. 執行狀態鏈

沿用 `docs/規劃_推薦投組系統V2.md` §2.0 的狀態鏈設計(這部分的設計是對的,予以保留):

```text
target list(L4a輸入) → OrderIntent(L4a輸出) → submitted/pending(L4b送出)
  → filled / partial / cancelled / rejected(L4b成交回報)
```

**`PositionState` 只在收到 `filled`/`partial` 或可驗證的 execution receipt 時才轉移。**
L4a 產生 `OrderIntent` 的當下**不**改動任何持倉、現金、成本狀態——決策與結果分離,
這是本規格唯一從 V2 全套架構繼承、且**不可妥協**的設計原則。

## 3. L4a — 決策層規格

### 3.1 觸發時機

月頻,dual100 驗證用的再平衡日(每月最後交易日收盤後)。**訊號用 close(t) 算,
輸出的 `OrderIntent` 標記執行日為 open(t+1)**——與 `exec_ret.fwd_x` 的定義逐字對齊,
不得有第二套時間慣例。

### 3.2 輸入

| 輸入 | 來源 | 備註 |
|---|---|---|
| 目標名單 | `real_composite` Top20% ∩ `c2` Top20%,ADV≥100萬,當月,再依 composite 百分位取前 `TOP_N=15` 檔 | 交集是用現有計分管線算,不重寫排序邏輯;`TOP_N` 濃縮是 2026-08-10 裁決,見 §10 第4項與警語 |
| 目前持倉 | 上一輪 L4b 輸出的 `PositionState` | 第一次執行時視為全現金 |
| 可用資金 | 使用者設定的總投入資金(一次性參數,不是每月輸入) | §6.3 裁決:100% 投入,不設現金緩衝目標 |

### 3.3 計算步驟(依序,不可跳步)

1. **目標權重**:名單內每檔等權 = `1 / len(名單)`。**不做任何額外集中度或產業上限
   調整**——H1–H5 驗證的就是純等權交集,沒有套任何集中度限制,L4a 也不准加(見 §8)。
2. **持倉差異**:比對「目標名單」與「目前持倉」→ 分成三類:
   - 續留(在兩邊都出現)→ 不動(除非張數因目標權重變動需要調整,見下)
   - 新增(只在目標名單)→ 買入意圖
   - 剔除(只在目前持倉)→ 賣出意圖(全數出清,不保留部分)
3. **金額換算**:目標權重 × 可用資金(含已實現的持倉市值,不是只算現金)= 每檔目標金額。
4. **張數換算**:目標金額 ÷ 當日參考價(收盤價) ÷ 1000,**無條件捨去取整數張**
   (MVP 只處理整股,零股見 §10 未決項)。捨去產生的剩餘金額計入現金,**不得**
   主動用來加碼其他股票或投資別的標的。
5. **薄量股上限檢查**:見 §5,可能下修某檔的目標張數。
6. **輸出 `OrderIntent`**:每筆含股票代號、方向(買/賣)、目標張數、決策當下的參考價、
   決策日期。**這是不可變快照**——一旦產生,L4b 執行時不得回頭修改。

### 3.4 輸出

`OrderIntent` 清單(JSON 或 parquet,一個決策日一份,append-only,**不可覆寫**——
比照 `universe_screen_daily.py` 的凍結件保護精神)。

## 4. L4b — 執行帳本規格

### 4.1 觸發時機

`OrderIntent` 標記的執行日(open(t+1))。

### 4.2 輸入

| 輸入 | 來源 |
|---|---|
| `OrderIntent` 清單 | L4a 輸出,當日待執行的那一批 |
| 執行日實際市場資料 | 當日開盤價、當日成交量(用於薄量股判斷,見 §5) |

### 4.3 執行規則

1. **成本模型**:手續費 + 證交稅 + 滑價,合計比照 H1–H5 驗證用的假設
   (0.47% 來回 + 滑價,H4 測到 0.60% 仍通過)。**不得**引入新的成本假設而不重新對照
   H4 的滑價敏感度結果。
2. **成交價**:以執行日開盤價為準(對齊 `exec_ret.fwd_x` 的 T+1 開盤執行慣例)。
3. **部分成交/未成交判斷**:見 §5,依薄量股規則決定 `filled`/`partial`/`rejected`。
4. **`PositionState` 更新**:只在拿到 `filled`/`partial` 的成交回報後才更新持倉、
   現金、成本基礎。`cancelled`/`rejected` 的單不留下任何持倉異動,只留稽核紀錄。

### 4.4 輸出

1. 成交回報(逐筆,含實際成交張數、實際成交價、狀態)
2. 更新後的 `PositionState`(見 §6)
3. 稽核軌跡條目(append-only)

## 5. 薄量股處理(優先項)

**背景**(2026-08-10 查證,已記錄進 `docs/現況總表_2026-08-09.md`):驗證過的雙確認
名單,連續 4 個月的 Top10 都有 2–4 檔 ADV20 僅個位數百萬 NTD 的極小型股。H1–H5 的
固定滑價假設(0.25–0.60%)對這種規模的股票很可能低估實際成本。**這不是邊緣情況,
是這個策略的常態,MVP 必須處理,不能延後。**

### 5.1 訂單規模上限(凍結規則,零自由參數的保守版)

**單筆訂單金額不得超過該股當日 ADV20 的固定比例上限 `ORDER_ADV_CAP`。**

- **`ORDER_ADV_CAP = 3%`(2026-08-10 使用者裁決,凍結)。** 沒有既有回測結果可對應
  這個數字(H1–H5 沒有模擬過訂單規模對市場的衝擊),是新風控參數的保守起點,不是
  算出來的最優值——理由:業界常見「低市場衝擊」經驗值約 3~10%,散戶級操作取低標;
  單一固定數字(不分級距)符合本節「零自由參數」設計。**允許事後依 shadow run 真實
  成交數據調整**(執行參數,不是選股邏輯,不受單發射擊制約束),但調整須留紀錄,
  不得靜默改動。
- 若「等權目標金額」超過 `ADV20 × ORDER_ADV_CAP`:**下修該檔的目標張數**到上限內
  (不是跳過整檔不買,也不是照原金額硬買)。
- 下修產生的資金差額計入現金,**不得**重新分配給其他股票加碼
  (那等於是在 L4a 之外偷偷改變了等權配置,會製造另一個「live 與驗證不一致」的落差)。

### 5.2 成交判斷(MVP 簡化規則)

MVP **不模擬**逐筆委託簿撮合(那需要 tick 級資料,H1–H5 §4 已明文排除)。改採
**規則式判斷**:

| 情況 | 判定 |
|---|---|
| 訂單金額 ≤ `ORDER_ADV_CAP` 上限內(§5.1 已下修過) | `filled`,以開盤價成交 |
| 當日該股完全沒有成交量資料(停牌/無交易) | `rejected`,記錄原因,**不得**假設用前一日價格填補 |
| 當日 ADV20 資料缺失 | `rejected`,fail-closed,不得跳過上限檢查直接送單 |

**不設 `partial`(部分成交)狀態於 MVP**——§5.1 的規模上限已經是「保守到不會缺流動性」
的簡化,MVP 階段先用「填滿或不做」二分,partial 狀態留到有真實委託簿資料時再做
(見 §10)。

### 5.3 稽核要求

每一筆因薄量股規則被下修或拒絕的訂單,**必須**在稽核軌跡留下:原始目標張數、
下修後張數(或拒絕原因)、當日 ADV20 值、觸發的規則名稱。**不得靜默下修不留痕跡**
——這正是本專案研究紀律反覆強調的「靜默改變口徑」問題,搬到執行層一樣適用。

## 6. PositionState 與稽核軌跡

### 6.1 PositionState(單一權威狀態)

```text
{
  as_of: 狀態時間戳(執行後的日期)
  holdings: {股票代號: {張數, 平均成本, 最近更新日}}
  cash: 現金餘額
  realized_pnl: 累計已實現損益
}
```

**只有 L4b 收到成交回報才能寫這個狀態,L4a 唯讀。**

### 6.2 稽核軌跡(append-only,不可覆寫)

每一筆 `OrderIntent` → 執行回報的完整鏈路都要留痕,格式比照本專案既有的
`GATE1_EXECUTION_MANIFEST.json` 風格(sha256 可追溯、明文記錄輸入版本)。
**目的**:之後要做「訊號說買 A、實際成交 B」的對帳,沒有這條鏈路對不了帳。

## 7. Fail-Closed 語義總表

| 情況 | 處置 |
|---|---|
| 目標名單算不出來(計分管線失敗) | L4a 整批中止,不產生任何 `OrderIntent`,不得用上月名單頂替 |
| 某檔股票當日無參考價 | 該檔 `OrderIntent` 標記為 `rejected`,其餘照跑,不得整批中止 |
| 執行日某檔無市場資料 | 該筆 `rejected`(見 §5.2),不假設價格 |
| `PositionState` 讀取失敗/損毀 | L4b 整批中止,不得假設「全現金」重新開始(那會憑空製造或消滅持倉) |
| 買賣後現金/持倉總額對不上 | 中止並報錯,不得靜默調整平帳 |

## 8. 明確禁止事項

- ❌ 加任何 H1–H5 沒驗證過的集中度/產業上限(§3.3-1),**`TOP_N=15` 濃縮是唯一的

- ❌ 加 L6a/L6b 事件與市場曝險模組——§6.3 已裁決不套 overlay
- ❌ 加 Z1-R 再進場、族群輪動——V2 規劃文件已明確標注暫停,未驗證

## 9. Synthetic Integration Test 規格

> **✅ 已實作(2026-08-10)**:`tests/test_l4ab_synthetic_integration.py`,14 個測試全過
> (含下方五項逐一對應的測試函式)。全部合成資料,不讀任何真實 TEJ_CACHE/market_cache/
> scores 快取,`LEDGER_DIR`/`TEJ_CACHE`/`MARKET_CACHE` 全部 monkeypatch 到 tmp_path。
>
> **寫測試過程中揪出兩個真的問題,已修在 `scripts/l4a_decision.py`**:
> 1. `compute_order_intent` 算「可投入資本」時只用目標名單裡的股票市值,**這次被
>    剔除、不在新目標名單裡的舊持倉市值完全沒算進去**——違反本規格 §3.3-3「可用
>    資金含已實現的持倉市值,不是只算現金」。整月全換股下每次都有剔除股,這個 bug
>    會系統性低估可投入資本。修法:`compute_target_list` 現在多回傳一份全池價格表
>    (`screen_by_composite_at` 本來就有,只是舊版算完交集後丟掉了),`compute_order_intent`
>    用它補上目標名單以外的持倉估值。回歸測試:`test_port_value_includes_dropped_holdings`
>    (手算數字釘住,並實測過如果退回舊邏輯這個測試真的會抓到)。
> 2. `compute_order_intent` 有個 `available_capital` 參數宣告了但函式體從未讀
>    它——資金其實全部來自 `pos.cash`,這個死參數只會誤導成「資金從這裡流入」,
>    已移除。

實作前必須先有 synthetic test(不碰真實資金/真實資料),證明以下五件事(逐字採用
`GPT answer.md` 第一輪提出的要求,這裡列成可驗證的具體斷言):

1. **可完整重播**:同一組輸入(目標名單+期初 PositionState+市場資料快照)跑兩次,
   輸出的 `OrderIntent`/成交回報/`PositionState` 逐位元相同。
2. **無同日偷看**:`OrderIntent` 的參考價只能來自 close(t),不得讀到 open(t+1)
   之後才存在的任何資料。
3. **守恆**:任一時點,`Σ(現金+持倉市值)` 的變動只能由「成交價差」與「成本」解釋,
   不能無中生有或憑空消失。
4. **決定性**:相同版本的程式碼+相同輸入 → 相同輸出,不含任何未 seed 的隨機性、
   不含 wall-clock 依賴。
5. **資料不足即 fail-closed**:人為構造「某檔當日無資料」「PositionState 損毀」
   等情境,驗證 §7 的每一條規則都真的觸發,不是靜默通過。

   別的縮減規則,三選一由使用者決定,規格本身不代為決定。

### 仍未決(1項,使用者主動保留)

4. **可用資金的實際金額** —— 直接影響 §5.1 上限的觸發頻率(資金越大,越容易撞
   薄量股的規模上限,實際配重會從「純等權」逐漸偏向「等權但受流動性上限修正」)。
   **這是使用者的個人資金決定,本規格不需要、也不會索取這個數字**——實作時以
   可設定參數(config value)的形式存在,填入時機由使用者自行決定,不阻塞開發。
