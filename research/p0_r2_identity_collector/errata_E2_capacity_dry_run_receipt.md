## 1. Problem this erratum fixes

**Correction (round 4):** round 3's version of this section overstated what the approved prereg actually says. Re-reading FR-31, FR-42, and NFR-7 as approved: **the prereg does not state that the NFR-7 capacity bootstrap dry-run is a `RunReceipt` with an `execution_mode=DRY_RUN` flag.** It does not define a receipt type for the dry-run at all — FR-31 defines `run_id`/identity only for what it calls a "run," NFR-7(a) requires "3 次試跑" (3 dry runs) to establish a bootstrap byte estimate, and neither cross-references the other. The correct problem statement is: **the approved prereg leaves dry-run receipt identity undefined / ambiguous**, not that it affirmatively adopted an `execution_mode` scheme that this erratum now overturns. (Round 2's design draft — a *design document*, not the prereg — was the one that introduced the `execution_mode=DRY_RUN` idea, as an attempt to fill this gap; that design attempt is what round 3 identified as flawed and this erratum formally withdraws. The prereg itself was never edited to contain it.)

Filling that gap by simply grafting a `execution_mode` flag onto the existing `RunReceipt` type (as round 2's design draft did) conflates two things that should never share a type:
- A **real evidence run** (`RunReceipt`), whose entire purpose is to be a durable, append-only, dual-copy-verified identity claim.
- A **capacity dry-run**, whose entire purpose is to measure bytes and then be deleted — it makes no identity claim about anything, and per FR-10/FR-36's spirit, nothing that is going to be deleted on purpose should ever be shaped like the type that is *specifically defined to never be deleted*.

Giving both the same receipt type, differentiated only by a field, is exactly the kind of subtle contamination surface this project's research discipline (`docs/研究紀律_ResearchDiscipline.md`) exists to prevent — a future maintainer skimming `run_receipt.json` files could mistake a dry-run artifact for real evidence if the `execution_mode` field were ever dropped, misread, or defaulted incorrectly.

## 2. Proposed changes to the approved prereg (for user approval)

### 2.1 New functional requirement (proposed FR-42a, inserted after FR-42 in §7)

> FR-42a: Capacity dry-run measurements required by NFR-7(a) are NOT `RunReceipt` instances and MUST NOT be assigned a `run_id` under FR-31's identity scheme. Each dry-run attempt MUST produce an independent `CapacityDryRunReceipt` (see Data Models), which is never written under `primary_root`/`mirror_root` (both remain conceptually undefined for a dry-run, not merely null-valued fields on a shared type) and is never counted toward `monthly_eligible_count`, `comparable_identity_count`, or any other evidence-facing counter.

### 2.2 Revised FR-31 (clarifying scope — proposed rewording)

> FR-31 (revised): Every `RunReceipt` — which by construction represents only LIVE evidence — MUST have identity `(as_of, collector_version, input_bundle_sha256)`, and a `run_id` deterministically derived from exactly that triple. `RunReceipt` carries no `execution_mode` field, because it is definitionally always a live evidence artifact; there is no dry-run variant of this type.

(This removes the round-2 draft's addition of `execution_mode` into the `run_id` derivation — that addition is withdrawn by this erratum, not merely superseded silently.)

### 2.3 New Data Model entry: `CapacityDryRunReceipt` (per-attempt, ephemeral)

Part of the temporary artifact set produced during a dry-run, deleted along with everything else in that temp directory after measurement (§2.4 below is the one part that durably survives it). Never located under `primary_root`/`mirror_root`. Carries `sizing_mode` (`P_ONLY_EVIDENCE` | `COMPARABLE_IDENTITY`) and `r_fwd_artifacts_included` (boolean, schema-tied to `sizing_mode`) — a Comparable-mode dry-run that omits R-FWD artifacts on any attempt is a Gate C-P failure, made mechanical at the schema level. See `collector_schema.json#/definitions/CapacityDryRunReceipt` for the frozen field-level schema.

**Payload/receipt hash separation (round 4, refined round 5), plus a fully-auditable capacity-projection field (round 8, replacing round 7's unaudited integer):** `CapacityDryRunReceipt.payload_files` is a **closed, named-file** manifest (the same `LiveOutputManifestPOnly`/`LiveOutputManifestComparable` type real evidence uses) of the **measured payload only** — excludes the receipt file itself and `capacity_dry_run_report.json`. `payload_sha256` is computed over that manifest and finalized **before** the receipt object is constructed — never self-hashing.

`CapacityDryRunReceipt` also carries `live_receipt_projection: LiveReceiptProjectionManifest` (round 8; replaces round 7's bare integer `projected_live_receipt_bytes`, which even allowed `0` and was never independently recomputable). **Round 7 of this erratum (round 9 of review) completes it**: the manifest's `placeholder_policy` and `actual_inputs` are now jointly EXHAUSTIVE over `RunReceiptSuccess`'s required-key set — round 8's version was missing `as_of`, the receipt status fields, `process_isolation`, `attempted_input_manifest`, `collector_version`, and `input_bundle_sha256`, so its "recomputable from these two alone" claim could not have held. The template is now identified by `ProjectionTemplateIdentity` (version + repo path + Git blob SHA-1 + content hash) rather than a bare hash, so a third party can actually OBTAIN the assembly algorithm, not merely fingerprint it. And new semantic check #16 requires the projection's `as_of`/`identity_status`/`output_hashes_equivalent` to agree with the enclosing dry-run receipt — previously a projection could describe an entirely different attempt. `projection_only: const true` still marks it structurally never a `RunReceipt`.

**Round 8 of this erratum (round 11 of review), two further corrections to `live_receipt_projection`:** (a) `PreflightObservation.lock_holder_pid`/`disk_free_bytes` — the two fields `placeholder_policy.attempted_input_manifest_placeholder` claims to hold at their "measured maximum-length legal value" — had no schema `maximum` at all through round 7 of this erratum, so that claim was an assertion the schema itself could not check; a real preflight value exceeding the assumed ceiling would have silently made the projection anti-conservative again. Both fields now carry explicit `maximum` bounds (`4294967295` / `9223372036854775807`), and semantic check #18 (extended) verifies the placeholder equals the bound exactly. (b) `actual_inputs.announcement_date_pit_status` (and the corresponding field on `ProjectedRunReceipt`) was `const:"BLOCKED"` unconditionally through round 7 — correct for `P_ONLY_EVIDENCE` sizing, but wrong for `COMPARABLE_IDENTITY` sizing: a live `COMPARABLE_IDENTITY` receipt is defined elsewhere in this design to require `announcement_date_pit_status=VERIFIED` (8 chars, longer), so unconditionally projecting the shorter `BLOCKED` (7 chars) under-sized every Comparable-mode capacity estimate in exactly the mode that needs the most space. The field is now conditioned on `identity_status`, matching the live type's own rule, and continues to be checked by validating the assembled object against `ProjectedRunReceipt` (check #12, extended). This does not touch Gate C-R's own block on the LIVE `RunReceiptSuccess` type, which remains structurally unsatisfiable for `COMPARABLE_IDENTITY` — the projection sizes a hypothetical future-viable receipt for NFR-7 capacity planning, and makes no claim about Gate C-R's current status.

### 2.4 New Data Model entry: `capacity_dry_run_report.json` (durable, small, versioned)

**Round 5 correction:** round 4's report stored only a scalar summary per attempt — the receipt object itself was gone once the temp directory was deleted, so `receipt_sha256` could be trusted but never independently *recomputed*. The report now embeds the **full** `CapacityDryRunReceipt` object per attempt (field `receipt`), with `receipt_sha256 = sha256_hex(canonical_json(receipt, sort_keys=true))` and `receipt_bytes = len(canonical_json(receipt, sort_keys=true).encode("utf-8"))` — both deterministically recomputable from `receipt` alone. These two fields describe `CapacityDryRunReceipt`'s **own** size — a small, ephemeral, non-evidence object — and remain useful for this wrapper's own reconstructibility audit, but are **not** part of the bootstrap formula (see below).

**Bootstrap formula, current state:** `attempt_total_bytes = receipt.payload_bytes + receipt.live_receipt_projection.projected_object_bytes`. Round 6 first added a receipt footprint to the formula at all (previously payload-only). Round 7 corrected which receipt type's footprint — the LIVE `RunReceiptSuccess`/`Failure`'s, not `CapacityDryRunReceipt`'s own (much smaller, irrelevant) size — but represented that LIVE footprint as an unaudited flat integer. Round 8 replaced that integer with `LiveReceiptProjectionManifest`; round 9 made that manifest genuinely recomputable (§2.3). `bootstrap_bytes_per_run = ceil(1.5 × max(attempts[*].attempt_total_bytes))` — this outer shape has been unchanged since round 4; only the definition of `attempt_total_bytes` has been corrected. Lives in `research/p0_r2_identity_collector/` alongside `collector_schema.json`, `prereg.md`, etc.

### 2.5 NFR-7 wording clarification (no substantive change, terminology only)

Replace every occurrence of "capacity dry-run" implying a `RunReceipt`/`run_id` with an explicit reference to `CapacityDryRunReceipt` and `capacity_dry_run_report.json`, so a future reader cannot conflate the two types by the prereg's own wording.

## 3. What does NOT change, and what this erratum now explicitly acknowledges DID change

**Correction (round 6, blocker 5; kept current round 8):** an earlier draft of this section claimed the bootstrap formula was simply "unchanged." That was wrong then, and would still be wrong if left describing any single historical version of the formula's input — this section is rewritten each round the formula's meaning changes, rather than left to drift stale (round 7's version of this section still described the round-5 intermediate `payload_bytes + receipt_bytes` form, itself already superseded — a stale-reference bug the user caught round 8). The accurate statement, as of this revision:

- The formula's **outer shape** — `bootstrap_bytes_per_run = ceil(1.5 × max(attempts[*].attempt_total_bytes))` — has been unchanged since round 4: still a 1.5× safety multiplier over the largest of 3 dry-run attempts.
- The formula's **input, `attempt_total_bytes`, has been substantively redefined twice, and each redefinition is part of what the user is being asked to approve, not a restated fact**:
  - Round 4: `attempt_total_bytes = payload_bytes` (receipt footprint omitted entirely).
  - Round 5: corrected to `payload_bytes + receipt_bytes` (`receipt_bytes` = `CapacityDryRunReceipt`'s own size) — round 4's version under-sized capacity by omitting any receipt footprint.
  - Round 7: corrected again to `payload_bytes + projected_live_receipt_bytes` — round 5/6's `receipt_bytes` measured the wrong receipt type (the small ephemeral dry-run wrapper, not the much larger LIVE `RunReceiptSuccess`/`Failure` that actually occupies disk on every real run).
  - Round 8: `projected_live_receipt_bytes` (an unaudited flat integer through round 7) is replaced by `live_receipt_projection: LiveReceiptProjectionManifest` — the same estimate, now disclosed rather than self-declared.
  - **Round 9 (current)**: that manifest's inputs are made genuinely exhaustive and its template genuinely obtainable, so the recomputability claim holds in fact and not only in intent. The formula's shape is unchanged from round 8; what changed is that its input can now actually be audited.
- The three exact P-B dates used for the dry-run are unchanged.
- Gate C-P's dependency on the dry-run completing is unchanged.
- No FR/AC/NFR numbering is renumbered or reused; FR-42a is an insertion, not a renumbering, to avoid disturbing existing cross-references throughout the approved document.
